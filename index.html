Prototype context Background & design rationale — personal reporting widgets ▾
What this screen does
Places a row of personal performance widgets at the top of the logged-in user's dashboard, directly above their existing work lists. The widget set is standardised with the Applications page: the same widgets appear on both screens, scoped to "My" here and "All" there. Widget 12 (RFI letters in progress) is exclusive to this screen. Everything below the widget row is the existing dashboard: the Admin, Active, Determine and Completed tabs and their grouped work queues.
Why designed this way
When Build AU becomes the primary assessment system, councils lose the performance reporting currently embedded in their ERPs (Pathway, TechOne, Authority). Foundation partner research (Canada Bay, North Sydney, Ryde, Hornsby) confirmed performance reporting is a baseline expectation rather than a differentiator. Individual planners asked for their own numbers in the place they already start their day, so the personal widgets sit on the dashboard rather than in a separate reporting area. Whole-of-council figures have moved to the Applications page, where the whole-of-council data set already lives.
Audience
Every user with an assessment caseload — Senior Statutory Planners, assessing officers, and team leaders looking at their own work rather than the team's. The widgets always describe the logged-in user, so no persona switch or role check is needed.
Design decisions
Widget selection, definitions and comparison behaviour follow the BASS: Performance Reporting — High-level Stories widget array. Ten widgets appear here: nine shared with the Applications page plus widget 12. Widget 5 is excluded per the spec as too close to widget 4. Widgets 7, 8, 10 and 11 are drawn with a dashed border and a "Later phase" tag — 7 until team performance periods are implemented, 8 until the planning-reform application types settle, and 10 and 11 together because both depend on stop-the-clock tracking. That leaves six widgets in Phase 1 here: 1, 2, 3, 4, 6 and 12. Counts (1, 2, 3) compare against the previous calendar month; widgets 4, 6 and 10 state a council-set target only. Cards are compact and carousel-paged (four visible of ten) so the work queue below stays reachable. Reference numbers are shown for review only and would not ship in the product.
Open questions
1. Six Phase 1 widgets and four deferred — is that the right split, and should the deferred ones appear at all in the shipped product? 2. Should the row load expanded or collapsed? 3. Widget 12 carries no comparison in the spec — is a bare count enough, or should it compare to last month too? 4. Should a team leader see their own caseload here, their team's, or a toggle? 5. With the "My" prefix removed, scope rests entirely on the "My performance" heading — is that signal strong enough?

Prototype context Background & design rationale — whole-of-council reporting widgets ▾
What this screen does
Adds a row of whole-of-council reporting widgets to the top of the Applications page, above the existing application list. The widget set is standardised with the user dashboard: the same widgets appear on both screens, scoped to "All" here and "My" there. Widget 9 (Avg lodgement days) is exclusive to this screen. A data export section extracts assessment and referral data for use in external reporting tools such as Power BI.
Why designed this way
These widgets began as a separate "planning leadership" dashboard. They have been folded into the Applications page instead, because that page already holds the whole-of-council data set the widgets describe — a leader reading a council-wide number and then wanting the rows behind it should not have to change screens. Personal caseload widgets remain on the user dashboard. Foundation partner research (Canada Bay, North Sydney, Ryde, Hornsby) confirmed councils need to monitor assessment speed in real time against tightening targets: 105 days for FY 25–26, reducing to 85 days by FY 27–28.
Audience
Any user with access to the Applications page. The widgets are no longer framed around a leadership persona — they are page-level statistics describing the council's whole application set, so they show the same figures to every user who can see the page.
Design decisions
Widget selection, definitions and comparison behaviour follow the BASS: Performance Reporting — High-level Stories widget array. Ten widgets appear here: nine shared with the user dashboard plus widget 9. Widget 5 is excluded per the spec. Widgets 7, 8, 10 and 11 are tagged "Later phase" — 10 and 11 together because both depend on stop-the-clock tracking. That leaves six widgets in Phase 1 here: 1, 2, 3, 4, 6 and 9. Counts (1, 2, 3) compare against the previous calendar month. Duration widgets carry a council-set target — gross.days.target, vet.days.target and net.days.target — because NSW targets are revised annually with the state government and each council sets its own. Widgets 4, 6 and 10 state the target only; widget 9 also states the variance against it. Every displayed value must be reachable via API so the same figures can be pulled into Power BI. Widgets report whole-of-council and do not follow the list filters; a "Whole of council" chip makes that explicit. The export sits below the application list and produces two flat CSV tables rather than one joined table, matching the structure councils need for Power BI ingestion.
Open questions
1. Fixed whole-of-council scope means a user can read "142 active" while the filtered list below shows three rows. Is the scope chip enough, or should the widgets follow the filters? 2. Should the row also appear on the Completed tab, where several metrics no longer apply? 3. Where do councils set the three target values, and who is allowed to change them? 4. Counts compare to the previous calendar month, so early in a month widgets 2 and 3 will always look down — is a rolling comparison better? 5. Widget 9 states its variance against target while 4, 6 and 10 state the target alone — should that be consistent? 6. Should any figures be role-restricted, or is whole-of-council performance open to all users?
